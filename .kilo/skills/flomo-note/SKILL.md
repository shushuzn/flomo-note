# flomo 卡片笔记（云端）

## Overview

把网页、文章、想法沉淀成统一格式的 flomo 概念卡，直接写入用户云端 flomo 账号。本地只存技能与工具（本文件、AGENTS.md、scripts、.mcp.json），卡片正文一律不落盘。

## 能力边界

flomo MCP 工具（实测可用）：`get_daily_review` `get_format_guide` `get_tag_guide` `memo_batch_get` `memo_create` `memo_recommended` `memo_search` `memo_update` `memory_context` `memory_user` `tag_rename` `tag_search` `tag_tree`。

### 读卡两工具的分工（硬限，2026-09-23 事故落定，先读此条再用工具）

| 工具 | 用途 | 返回内容 | 能用来做什么 |
|---|---|---|---|
| `memo_search` | **发现**卡片 | **截断**（`content_truncated: true`，含"…[此处省略 N 字]…"） | 只能判断"库里有没有相关的卡、有哪些卡" |
| `memo_recommended` | **发现**近邻卡 | **截断** | 同上 |
| `memo_batch_get` | **读取**卡片正文 | **全文** | 唯一可用于判断正文内容、字数、是否违规、供合并/更新依据的工具 |

- **判断某张卡正文有什么，只能用 `memo_batch_get`**（参数 `{"ids":["...","..."]}`，可批量）。
- **严禁**用 `memo_search` 的截断内容去判断"这张卡讲了什么""有多长""有没有违规内容""能不能作为合并主卡"——截断内容会让人误以为卡片"只有这么多"，从而看不见已混入的异事件内容。
- **严禁**凭截断内容报告字数。字数取 `memo_batch_get` 全文实测长度或 `word_count` 字段。

写操作只有三个：

- `memo_create` — 新建卡片。
- `memo_update` — 覆盖某张卡（整卡替换，不保留旧文）；把卡清空为空白笔记也走本工具。
- `tag_rename` — 全库改标签名。**异步生效**：返回的 `matched_memos` / `updated_memos` 表示已受理，卡片标签稍后才被刷新，立即读回仍会看到旧标签；禁止据"读回未变"立刻判定失败并逐卡兜底改挂（会与后台任务撞车，把同卡写成重复标签）。正确做法：稍后重采 `tag_tree` 或按旧标签 `memo_search` 复查确认清零，确有残留才逐卡 `memo_update`，且重写首行时必须对标签 token 去重（单次检索上限 50 条，大簇不能靠一次搜索断言全量）。

### 无删除、无合并

- **无 `memo_delete`**：flomo 不提供从云端移除卡片的 API，**物理删除只能用户在 App 内手动完成**。技能侧绝不调用删除，也不主动提示用户去删。
- **无 `memo_merge`**：`memo_update` 是覆盖不是并卡，`tag_rename` 只能并标签名不能并卡片。**跨卡合并不依赖 API 级合并**，而是"并入主卡（`memo_update` 重写）+ 清空冗余源卡（`memo_update` 空白）"两步组合完成，全流程免授权（见「7. 复盘 · 跨卡合并」）。

### 清空 ≠ 删除（清空免确认）

- **清空** = `memo_update(id, content=' ')` 把正文改为空白笔记（必须单空格，空串被忽略）；卡片仍在云端，只内容被抹除，日后仍可用 `memo_update` 重新写入正文。
- **删除** = 从云端彻底移除卡片，技能无此能力。
- **口径（2026-09-18 改定）**：清空属常规写云动作，与覆盖正文同为 `memo_update` 写入，**免确认直接执行**；只有物理删除须用户明确授权，而删除只能用户在 App 内手动完成。
- **副作用**：清空会把该卡标签一并置空，只挂在它上面的独占标签随之从标签树消失。因此引用任何标签簇名前必须重新 `tag_tree` 现采，不得凭历史记录或旧日志里的簇名引用。
- **范围确认**：清空前先用 `memo_search` / `tag_tree` / `memo_batch_get` 确认是哪一张或哪几张，避免误清本就合规的卡。

## 执行铁律

1. **只读直接做，写云免确认**。只读工具（`memo_search` / `tag_tree` / `memo_batch_get` / `memo_recommended` / `get_*` / `memory_*` / webfetch / websearch）无需请示。写操作（`memo_create` / `memo_update`（含清空空白卡）/ `tag_rename`）一律免确认：抓取 → 查重 → 自检 EXIT=0 后直接写云，不展示等批。**收尾的「标签建议」同属免确认写云动作，不得只提不做**：本轮提出的改名、归并、补挂、拆分须在当轮直接调 `tag_rename` / `memo_update` 执行完、复查生效后再写入收尾结论，并在结论里报告已执行结果（改了哪几张、旧标签是否清零）；唯一例外是需用户点方向的多义合并（如两个都成立的簇名谁并入谁），此时明示待定向不外推。**禁止凭个人判断跳过写卡**：用户发链接即视为"需要写卡"，抓取成功且能提炼出任何事实、数据或观点就必须写云，不得以"内容单薄""不值得"为由跳过；仅在抓取完全失败且无替代来源时方可跳过并说明原因。
2. **来源实实在在，且必须真正读回原文**。带来源 URL 的卡片，该 URL 必须已真实抓取并基于实际内容写作。**抓取到的内容必须用 Read 工具读回正文文件、逐条对照后才能落笔**：WebFetch 的一句话摘要、模型记忆、按域名或标题推演一律不算已抓取。抓取失败、空 SPA 壳且无外链可追时，禁止写云。预印本只抓到摘要页等同未抓取，必须按流程第 1 步「预印本正文优先」取到正文（正文通道穷尽仍不可得时的摘要写卡例外，见同条末项）。
3. **flomo 调用一律走脚本、且逐次手动调用**。统一用 `python scripts/flomo_client.py <tool> --file <json路径>`（从文件读 JSON，避免 PowerShell 把引号转成全角），不写内联 JSON。每次查重、查树、写云、复盘都是**单次调用一次脚本并读该次原始返回**；禁止用内联 python、PowerShell `for` 循环、`&` 拼接等批处理方式把多次调用串成一次执行（批量循环会掩盖单次结果、偏离逐次现查流程）。
4. **写云前必查重**，并显式报告查重结论（命中什么 / 无重复），不得敷衍。
5. **文档改动须附真实 hash**。称"已提交 / 已推送"必须给出真实 commit hash，不口头虚称。
6. **单卡字数硬限**：单卡正文（含标签段）不得超过 20000 字；超出须精简，禁止超限写云。
7. **禁止关联卡片硬限**：卡片正文不得提及、引用或关联其他 flomo 卡片（写"与已建卡的 XXX 形成…"、设"关联卡片"段落、引用其他卡 id / 标题 / 内容等均在禁止之列）；禁止用 `linked_memos` 字段设置卡片间关联。每张卡独立成文，不依赖其他卡上下文，不跨卡串联归纳。
8. **概念卡硬限**：每张卡围绕某一概念 / 主题 / 事件 / 企业记录与整理，后续进展用 `memo_update` 覆盖更新，禁止为同一概念新建平行卡。
9. **单卡单事件硬限**：一张卡只记录一个事件 / 主题 / 企业；多条目链接或一文多事件须按条目拆成多张独立卡，禁止跨条目汇总、禁止把多事件塞进一张卡。
10. **读卡必须取全文，禁用截断内容（硬限，2026-09-23 事故落定）**：`memo_search` 返回的 `content` 是**截断快照**（带 `content_truncated: true`，中间以"…[此处省略 N 字]…"占位），**不得据此判断卡片实际内容、字数或是否违规**。凡要读写某张既有卡的正文（合并、覆盖更新、格式核查、复盘自查），必须先 `memo_batch_get`（参数 `{"ids":[...]}`）取回**全文**再操作。事故根因：连续多轮误把 `memo_search` 的截断内容当全文，导致写入的异事件内容长期"看不见"，合并与更新在错误认知上连续发生。
11. **字数只认实测（硬限）**：报告卡片字数一律取自 `memo_batch_get` 返回文本的真实长度或 `word_count` 字段；**严禁凭截断内容估算、严禁凭印象报"X 字 → Y 字"**。无实测数据时如实说明"未实测"，不得编造。
12. **同一事件判定：以事件为准，不以主题为准（硬限）**：判断两篇材料是否同一事件，依据是**主体 + 动作 + 时点**三项是否同一（同一次发布、收购、财报、政策出台、事故、开庭）；**仅"同属某领域/某主题/某条治理主线"不构成同一事件**。反模式：把"分别发生在不同时间、由不同主体发布的多个政策/发布"因共享某主题而并为一张卡，产出"进程卡""发布潮卡""产业格局卡"等综述汇编——一律视为违反第 9 条。
13. **合并只并事件本体，不并载体素材（硬限）**：合并/更新时，只并入**属于该事件本身**的事实、数据与因果；报道中作为**论证素材**出现的举例、判例、类比、他方案例、延伸评论，**不得因"出现在同一篇文章里"而写入本卡**。反模式：把"某法修订草案征求意见"的报道里用来举例的**司法判例**写进该立法卡。
14. **合并后必须回读全文验收（硬限）**：任何 `memo_create` / `memo_update`（含清空）完成后，若属合并或覆盖更新，须 `memo_batch_get` 回读该卡全文，逐项确认：① 首尾同属一个事件；② 无载体素材混入；③ 无他卡内容串位；④ 字数与预期一致。验收不通过则当轮修正，禁止只凭"已写入 id"宣告完成。
15. **素材保留（硬限）**：抓取原文、草稿、被替换的旧卡全文等中间文件，须保留**最近若干轮**（至少当次会话的全部轮次），不得在同一轮收尾时即刻全删；清理只清与近轮无关的历史文件。事故根因：上一轮 `CLEAN_OK` 删掉了当轮素材，导致下一轮无法回溯核对写入内容。

## 卡片格式

结构：首行标签段单独成段，第二行写概念名称（简明概括卡片主题的名词或概念，如"马尔科夫链"），空一行接正文。

```
#标签/细分
<概念名称>

<直接写结论句，例如：MotherDuck 于 2026-08-25 收购 Tower，补齐数据工程运行时>

要点：
- 要点一（依据）
- 要点二
```

- **占位符必须替换**：上方尖括号 `<...>` 是写给执行者看的说明，落卡时一律换成真实内容；禁止把"一句话核心结论"这类格式提示词当正文前缀写进卡片。
- **结论先行**：首段直接给结论句，不带"一句话核心结论："之类模板前缀。
- **`要点：` 是允许的结构标记**；其它纯说明性文字不得写入。
- **无来源行、无状态行（硬限）**：正文禁止任何来源 / 作者 / 报道 / 参考信息独立行，也禁止任何状态 / 进展信息独立行，变体包括但不限于"来源：""作者与来源：""信息来源：""数据来源：""参考来源：""资料来源：""内容来源：""新闻来源：""原文来源：""引用来源：""来源链接：""参考资料：""参考文献：""报道：""报道信息：""报道来源：""状态：""当前状态：""进展状态："；这些信息融入正文对应要点，或直接省略，禁止巧设名目绕过格式要求。
- **禁止卡片载体信息（硬限，2026-09-22 事故增补）**：卡片只写**概念 / 事件本身**，禁止交代"这张卡是从什么载体上抄下来的"。无论放在首段括号、要点句内还是行尾，一律禁止，无豁免位置。典型违禁表述：截图 / 截屏 / 录屏 / 屏摄、讲义 / 课件 / 幻灯片 / PPT / 板书 / 续页、字幕 / 批注 / 听课笔记、第 N 页 / 10–11/36 页 / N/M 页、UP 主 / B 站 / 哔哩哔哩 / 直播间 / 课程记录 / 讲座、公众号 / 视频号 / 小程序 / 推文、"如图 / 见图 / 上图 / 该图所示"、带日期的"XX 课程讲义，定义 3"式出处括号。载体上没有的信息**直接省略**，禁止用"截图未展开""板书从略""页码待补"之类说法变相保留。
- **区分"卡片载体"与"事实来源"（口径）**："据沈阳市纪委监委消息""新华社报道""通报称"是**事件自身的信息来源与程序要素**，属于内容，事件卡（反腐 / 政策 / 企业公告等）合法保留、必要时写入要点；"B 站直播截图""课程讲义第 9 页"是**你手上这份材料的物理形态**，属于元信息，与概念无关，一律删除。判据：换一个人从同一篇文章 / 同一场发布会取同样的内容，这句话是否仍然成立且有意义——成立即事实来源可留，不成立即载体信息必删。
- **其余硬限同源于执行铁律**：单卡 20000 字上限（第 6 条）、禁止关联卡片（第 7 条）、概念卡一概念一卡（第 8 条）、单卡单事件（第 9 条）。
- **flomo 富文本实测**：支持加粗 `**文字**`、高亮 `<mark>`、下划线 `<u>`、两级列表、空行分段；不渲染标题、引用、代码块、链接、表格、图片。
- **公式用 Unicode**（∑ μ →），不写 LaTeX 美元符。

## 标签规则

- 首行标签段，多个 `#标签` 用空格分隔，**每个都要带 `#`**（裸词不进标签系统）。
- **子标签必须带主前缀**：写 `#思想/协调博弈`，不裸写 `#协调博弈`（后者会建出独立顶层）。
- **层级严格两级（硬限）**：合法形态只有 `#顶层/二级`（例：`#科技/安全`、`#思想/协调博弈`）。三段及以上一律非法（`#科技/安全/邮件认证` 不可）。主题看似需要第三层时二选一：① 并入既有二级（邮件认证 / 钓鱼 / 攻击面本就含在 `科技/安全` 定义内，直接落 `科技/安全`）；② 在合适顶层下新建二级（仍是两级，免确认，但须先查近邻确认无既有簇）。宁可在二级内用正文细分，绝不下探层级。
- **顶层禁泛指词头**（`#概念/`、`#方法/`）；禁 emoji 与特殊字符；英文词用下划线（`#Apple_seed`）。
- 新建顶层或二级前先 `memo_search` + `tag_tree` 现查近邻确认无既有簇；**新建、重命名、合并标签一律免确认**；禁止为"能复用"而硬套既有标签凑数。
- **具体当期主题 ≠ 纯概念筐**：`/方法论`、`/概念` 这类二级只收"研究怎么做"的元层面（框架、范式、通用方法）；某政策、某事件、某产品的当期解读严禁塞入，必须落到具体主题二级（无则新建）。

### 标签错配防御（硬限，不可跳过）

1. **核实主体所属**：定标签前确认主体的真实分类（饮料 / 食品 / 美妆 / 日化 / 科技 / 媒体等），不按模糊印象硬套。例：德芙是巧克力（食品），塞进"快消饮料"即违规。
2. **匹配事件本质而非事件载体**：按事件核心性质选标签，不按涉事品牌的行业大类硬套。例：德芙七夕暧昧文化争议本质是青年文化与婚恋价值观事件 → `#文化/青年文化`。
3. **不合内容绝不硬塞**：既有标签不精确匹配主题时必须新建更精准标签，不得以"语义接近"为借口硬套。例：主题是液冷服务器，即使存在 `#科技/算力硬件` 也不能塞——只有确认主题精确属既有标签定义范围时才复用，否则现查后免确认新建。既不允许反问用户，也不允许"宁塞勿新"。
4. **内容严格来自原文**：原文是事件报道就不写"方法论""启示"等原文没有的分析；原文是方法论文章才提炼方法论。原文没有的要点一律不写。

## 流程

### 1. 抓取

- 以 webfetch 为主；SPA 站或清单站补 `curl -L -A "Mozilla/5.0"`；同名对象按域名、作者、用途消歧。
- **抓回即读回**：HTML/PDF 抽取成正文文件后必须用 Read 读回全文，未读回不得进入提炼与写作（见执行铁律第 2 条）。
- **预印本正文优先（阻塞）**：arXiv / bioRxiv / medRxiv / ChemRxiv / SSRN / OpenReview / ResearchGate 等，摘要页不作首选写作依据——摘要只够判断值不值得写卡，不足以支撑要点，必须先穷尽正文通道：
  - arXiv：把 `/abs/<id>` 换成 `/html/<id>v<N>` 抓 HTML 全文；无 HTML 时退 `https://ar5iv.labs.arxiv.org/html/<id>`，再退 `https://arxiv.org/pdf/<id>`。
  - 其它预印本：走站内 Full text / PDF / HTML 入口，或退到作者主页、机构仓库（HAL、高校 repository）的全文版。
  - **SNI 被 RST 时走域名前置（硬限 · 2026-09-11 本机实测）**：TCP 能建连但 TLS 立即被重置（curl 报 `schannel: failed to receive handshake, SSL/TLS connection failed`、python 报 `ConnectionResetError [WinError 10054]`）时，先做 SNI 变量对照——同一边缘 IP 换 SNI（如 `www.bing.com`）能握手成功即判定为 SNI 关键字阻断而非网络不通。确认后改走 `python scripts/sni_fetch.py <url> <out_path>`（把 SNI 换成无关域名、HTTP Host 头保留目标域，Fastly 按 Host 路由故内容照常返回，自动跟随重定向并去 chunked/gzip）；取回的 PDF 用托管 venv 的 `pypdf` 提正文（`C:/Users/35234/.workbuddy/binaries/python/envs/default/Scripts/python.exe`，已装 6.x）。不得因 curl / WebFetch 失败就断言"正文拿不到"并跳过写卡；此通道也失败时才进入下一条补 search 与跳过判定。
  - 正文得手时，要点必须落在正文层级：定理与命题的编号和陈述、模型与方法名、关键参数与设定、实验条件与结果、附录结论等；只复述摘要的泛泛表述不算正文写作。
  - 正文穷尽通道仍不可得（超时 / 403 / 登录墙 / PDF 不可解析）时：先补 `search` 找正文级转述（作者博客、项目页、会议 slides、引用该文的综述）；仍无正文级来源时**可依据摘要写卡**（唯一例外）——要点严格限于摘要明确陈述的事实与数据，禁止凭标题臆测或推衍摘要未述的细节，收尾必须显式注明"本卡基于摘要写作（正文不可得）"，待正文可得后补抓并 `memo_update` 更新。

### 1.5. 网络搜索验证（阻塞）

- 主体若为专业术语、数学概念、科学名词、机构简称、专有名词（分形名称、模型代号、定理名、产品系列、组织名等），必须用 `search` 现查标准名称与定义，不凭原文简称或图片特征臆测。
- 查证项：标准术语（中英文）、命名来源或发明者与首次提出时间、关键参数（维数、缩放因子、迭代规则等）；结果融入正文对应要点。
- 抓取失败或内容不足以提炼事实时，补 `search` 搜相关内容作替代来源；无替代则跳过写卡并说明原因。

### 2. 提炼

滤除营销话术，保留事实、数据与因果链；不编造（见标签错配防御第 4 条「内容严格来自原文」）。

- **图片 / 截图输入只提炼内容，不记录载体（阻塞）**：用户发来课程截图、直播画面、板书、PPT 页、公众号长图等图片时，图片只是**取材通道**，卡片只写概念本身。禁止把载体与取材细节写入正文——平台与账号名（B 站、UP 主、公众号）、材料形态（讲义 / 课件 / 板书 / 字幕 / 批注）、定位信息（第 N 页、10–11/36 页、"续页""如图"）、带日期的出处括号（"（2026-09-20 范畴论课程讲义，定义 3）"）一律删除；图片糊掉或缺页导致某条信息无法确认时，该条**直接不写**，禁止用"截图未展开""板书从略"交代缺失。定义、定理、公理各自独立成卡，同一定理的连续续页用 `memo_update` 覆盖式重组，不做贴膏药式追加。

### 3. 定标签（含筐型判断，阻塞）

1. 先取标签树：按「本地与治理 · 标签树本地留存」比对数量——`tag_tree` 现采云端数量（`limit` 传 2000 拿全量）与本地 `tag_tree.txt` 一致即直接用本地 txt，不一致才现采云端并覆盖更新本地 txt。
2. 命中既有簇优先复用，但**只在与主题精确匹配时复用**；不精确就必须新建更精准标签（见标签错配防御第 3 条「不合内容绝不硬塞」）。
3. 避开纯概念筐：具体当期主题必须落到具体二级，无则新建。
4. 新建二级先现查近邻确认无既有簇；标签深度严格两级，不得产生 `#顶层/二级/三级`。

### 4. 查重（阻塞）

- 两路并查：`memo_search` 关键词扫 + `tag_tree` 列出该主标签下的细分逐条比对（主标签维度检索常返回 0，必须退回关键词加逐条比对）。
- 判定：两路均无命中 → 新建；完全重复 → 指向原卡；部分重叠 → 更新原卡。
- **同事件只留一张卡（硬限）**：同一事件（同一次发布、收购、财报、政策、事故、开庭）只保留一张卡。无论新到几篇报道、拆出几个视角（商业、架构、评测、生态、财务），全部并入同一张卡，用 `memo_update` 覆盖式合并（重组织语言、消除重复、按逻辑重排）；严禁为"不同角度 / 补评测 / 补商业 / 补生态"新建平行卡。反模式：同一事件连建"架构""商业""评测"三张卡，一律视为误操作，必须并为一张。
- **事件边界判定（阻塞，先于合并决策）**：合并前必须先按「执行铁律第 12 条」判定"是否同一事件"——**主体 + 动作 + 时点**三项同一才算同一事件。"同属某主题"不构成合并理由。判定为同一事件 → 可合并；判定为不同事件 → 各自独立成卡，**禁止仅因共享主题而合并**（否则产出"进程卡""发布潮卡""格局全景卡"等综述汇编，违反执行铁律第 9 条）。
- **合并内容边界（阻塞）**：合并时只并**该事件本身**的内容。报道中作为论证素材的举例、判例、类比、他方案例、延伸评论一律**不并入本卡**（见执行铁律第 13 条）；素材若本身构成独立事件且确有记录价值，另建独立卡，不得借合并塞入。
- **合并前必读全文（阻塞）**：对被并入的卡与目标主卡，均须 `memo_batch_get` 取全文后再决定并什么、删什么（见执行铁律第 10 条）。**禁止凭 `memo_search` 的截断内容做合并决策。**
- 只有当新内容与原卡是真正不同的主体或事件时才新建。
- 同时受「执行铁律第 9 条 单卡单事件」反向约束：一张卡也不得塞入多件独立事件。
- 每个关键词、每条标签检索都单独执行一次 `python scripts/flomo_client.py memo_search --file ...` 或 `tag_tree`，并读该次原始返回判断，禁止批处理（见执行铁律第 3 条）。

### 5. 写作

按「卡片格式」写 1 条。

### 6. 写云前自检（阻塞）

- 命令：`python scripts/validate_memo.py memo_body.txt`（从文件读；也支持 `--file` 别名、`--content "..."`、`--create create.json`；传入 JSON 时自动抽取 content，兼容顶层 `{"content": ...}` 与 JSON-RPC 信封两种形态；读文件走 utf-8-sig 容忍 BOM）。
- 必须 EXIT=0（0 ERR）才允许写云；任一 ERR 先改再写，禁止把云端当草稿反复 `memo_update`。自检通过即调 `memo_create` 写云，免确认。
- 质检项（ERR 任一命中即阻塞写云；WARN 只提示不阻塞）：
  - **标签严格两级（ERR）**：三级及以上或裸顶层直接判错，与「标签规则」同源。
  - **结构完整（ERR）**：首行标签段、第二行概念名称非空、标题后空行、正文非空。
  - **flomo 不渲染语法**：代码块与图片语法判 ERR；标题、引用、表格、链接判 WARN。表格只认三种真形态（分隔行 `|---|---|`、竖线包裹行 `| a | b |`、空格包围的竖线成组 `a | b | c`）；紧贴文字的竖线（绝对值、集合势、条件概率如 `P(A|B)`）一律放行不误报。
  - **正文脏标签（ERR）**：flomo 会把任意 `#xxx` 当标签，`#词` / `#数字` 判错，含 http 的行整行豁免；正文里的 `/` 斜杠属正常书写（如「Mori/Siu–Yau」「消失/刚性/估计」），不作脏标签扫描。
  - **占位与生造来源（ERR）**：example.com、待补、placeholder、TODO、lorem 直接判错。
  - **预印本摘要依赖（WARN）**：出现"摘要称 / 摘要显示 / 摘要指出 / 摘要提到 / 据摘要 / 摘要中"等表述时提示回查是否漏抓正文；该句确为正文级陈述可忽略。
  - **旧格式遗留（WARN）**：来源行与状态行仍是卡片格式硬限，但质检只提示不阻塞。仅在三条件同时成立时提示：① 行首（允许 `-`、`*`、`~`、`•` 与 `1.` 序号）匹配「白名单修饰词（当前 / 进展 / 信息 / 内容 / 数据 / 新闻 / 原文 / 引用 / 参考 / 资料 / 文献 / 报道 / 官方 / 文章 / 作者与 / 链接 / 网址）＋ 状态|来源|报道|出处|资料|文献|参考 ＋ 可选后缀（链接 / 资料 / 文献 / 信息 / 地址 / 网址 / 说明）＋ 半角或全角冒号」；② 该行位于卡片最后两个非空行；③ 冒号后内容不超过 200 字或含 http 链接。因此「电力来源：」「收入来源：」等主语式要点与正文中间的「状态：」一律不报。命中时人工判断：正文要点可忽略；确为卡片级来源或状态行则删除该行，信息融入对应要点或省略，禁止巧设名目保留。
  - **卡片载体信息（ERR）**：2026-09-22 事故加固，对应「禁止卡片载体信息」硬限。三层判定防误伤——① 行内出现强载体词（截图 / 截屏 / 录屏 / 屏摄、讲义 / 课件 / 幻灯片 / PPT / 板书 / 字幕 / 批注 / 听课 / 续页 / 原图 / 配图、UP主 / B站 / bilibili、第 N 页与 `10–11/36 页` 式页码、如图 / 见图 / 上图 / 该图）直接判错；② 取材标注词（公众号 / 视频号 / 小程序 / 哔哩哔哩 / 抖音 / 快手 / 小红书 / 直播 / 录播 / 讲座 / 课堂 / 课程 / 订阅号 / 推文）只在**括号式注释**内出现才判错，行内正常书写放行，避免误伤「微信公众号是腾讯的创作平台」这类以平台为本体的概念卡；③ 括号内歧义词（视频 / 音频 / 回放 / 演讲 / 发布会 / 访谈 / 播客）只 WARN 人工判断。概念名称行含强载体词时只 WARN（平台 / 企业名作概念名合法）。新闻事实用语（报道 / 消息 / 通报 / 官网 / 作者）不在检测范围，故"据沈阳市纪委监委消息""新华社报道"等事件卡事实来源一律不报。已判错的行不再叠加同类提示。

### 7. 复盘（写卡后必做，须现查）

三路逐一现查并判断：`memo_search` 关键词扫近邻、`tag_tree` 列同主标签细分、`memo_recommended`（**传本卡 id**，limit 建议 20，只读校验——它按本卡返回语义近重复，专补关键词搜不到的情况；不写 `linked_memos`）。

> **注**：`memo_search` 与 `memo_recommended` 返回的 `content` 均为截断内容，**只能用于"发现有哪些卡"，不能用于"判断某卡正文有什么"**。凡涉及某卡正文的判断，一律 `memo_batch_get` 取全文（执行铁律第 10 条）。

- **本卡全文自查（先看，硬限）**：必须 `memo_batch_get` 读回本轮所写卡的**全文**，逐项核对：① 首尾是否同属一个事件；② 是否混入载体素材（举例/判例/类比/他方案例）；③ 是否串入他卡内容；④ 字数是否与预期一致。发现任一问题当轮修正，不得只凭"已写入 id"宣告完成。

- **新建合理性复查（先看）**：本卡是否其实是同一主体的新方面、本应更新既有卡？是 → 向用户报告"应更新原卡而非新建"并提议 `memo_update`，本轮新建视为误操作。
- **错配核查（先看）**：本卡标签是否把具体主题塞进了 `/方法论`、`/概念` 等纯概念筐？是 → 当轮直接建具体二级并 `memo_update` 改标签，不得自欺写"归入既有"。
- **硬塞核查（先看）**：本卡标签是否与主体实际类别不符（巧克力→饮料、媒体事件→产业方法论）？是 → 当轮直接 `memo_update` 改为正确标签，不得静默覆盖。
- **标签归并**：两卡仅标签命名不同、本质同类 → 当轮直接 `tag_rename` 归并（异步生效，按「能力边界」的 `tag_rename` 条复查清零后再决定是否逐卡兜底）。
- **标签补挂 / 拆分**：发现具体主题被载体或宽簇吞掉（如车企机器人只挂 `#科技/机器人`、执法通报与法院裁判同挂 `#法律/普法警示`）→ 当轮直接新建二级或改挂相应卡片（`memo_update` 只重写首行标签段、正文原样保留、标签 token 去重），不得留成"建议"。
- **跨卡合并（免授权，硬限）**：发现同一事件被拆成多张卡、或与既有卡实质重叠时，**直接执行合并，无需向用户请示**——选定内容更完整的一张为主卡，用 `memo_update` 把其余卡要点重新组织后并入主卡（合并同类要点、消除重复、按逻辑重排，禁止末尾追加），再把冗余源卡 `memo_update` 清空为空白笔记。全流程免确认，属常规写云动作（见「清空 ≠ 删除」）。**合并前必须先按执行铁律第 12 条判定同一事件、按第 10 条读全文、按第 13 条划清内容边界**；合并后按第 14 条回读全文验收。仅在**多义合并**（两张卡都够格当主卡、谁并入谁影响信息组织）时才停下问方向，且须给出明确建议。合并完成后在复盘结论中报告：主卡 id 与合并后字数（实测）、被清空的源卡 id、标签处理结果。绝不声明已合并两张卡（无 `memo_merge`）。
- **违规汇编卡拆解（免授权，硬限）**：复盘时发现既有卡本身是**多事件汇总**（"进程卡""发布潮卡""产业格局卡""多条目盘点"等），按执行铁律第 9 条属违规，须当轮处置：① 先 `memo_batch_get` 读全文，按**事件边界**（主体+动作+时点）切分出各独立事件；② 逐张新建独立卡（每张走查重 + 自检 EXIT=0）；③ 其中的历史沿革/背景数据若归属某张既有主卡，回填该主卡（重组并入，不末尾追加），否则并入对应事件卡作背景；④ 汇编卡本身若内容已全部被专属卡覆盖且无独有信息，直接清空；若有独有信息则改为只记其核心事件。拆解后须现采 `tag_tree` 核对标签计数变化并报告。
- **确无近邻**：写明"已现查 tag_tree 与关键词，无需调标签或聚合"，禁止只写"本轮无 memo 需更新"。
- **新建卡推荐**：复盘结论为"新建合理"时给 2-3 条可新建卡片推荐（主题、标签、核心论点），格式见「写卡收尾输出格式」第 3 点；判定"应更新原卡"则跳过。
- **复盘建议禁区（硬限）**：收尾的「标签建议」一条落点仅限标签改名、归并或调整，严禁提议新建卡片（新建推荐由专门一项负责，二者不重复）；严禁提议改动 SKILL.md、AGENTS.md、顶层词表、脚本等技能文档——词表补登与文档修订一律等用户另行指令，或走独立改动流程（commit + 真实 hash + push）。建议中不得提及、引用或关联其他 flomo 卡片，禁止使用 `linked_memos`。

### 8. 更新云端（免确认）

- `memo_update`（覆盖式）或 `tag_rename` 直接执行，无需授权；无待更新时明示"本轮无 memo 需更新"。
- **更新必须重新组织语言**：新内容融入既有结构，合并同类要点、消除重复表述、按逻辑重排；禁止在末尾机械追加要点（"贴膏药"式更新）。
- **取最新、删过时（硬限）**：用最新数据替换旧数据，删除已被覆盖的时间节点、旧统计与旧状态描述（伤亡数据只留最新节点，不留逐日旧值），禁止为"保留历史"堆叠旧数据造成笔记膨胀。
- **格式合规修正（硬限）**：更新已有卡片必须先回读原笔记，按「卡片格式」检查（首行标签段、第二行概念名称为简明概括主题的名词、无来源行与状态行、标签严格两级、单卡不超 20000 字）；原笔记不合规时，必须在本次 `memo_update` 中一并改到合规，不得保留旧格式遗留。

## 写卡收尾输出格式（固定，逐项必填）

每轮写卡结束按序回复，各项都必须出现，无内容显式写「无」，禁止静默省略。

1. **复盘结论**：一句话写清三路现查结论（新建合理 / 应更新原卡 id=xxx / 需改标签），并说明跑了哪几路（`memo_search` 关键词、`tag_tree` 同主标签、`memo_recommended`）。
1.5. **本轮全文自查结果（必填，硬限）**：报告 `memo_batch_get` 回读本轮所写卡全文的核对结果——① 首尾是否同属一个事件；② 有无载体素材混入；③ 有无他卡内容串位；④ 实测字数（写"实测"二字，禁止估算）。发现并修正了问题的须一并说明改前改后。**未做此项自查不得进入下一项。**
2. **标签建议**（一条，落点仅限标签改名、归并、补挂、调整）：必须针对本卡当前标签的实际问题——命名不准、与既有标签本质同类需归并、层级需调整、或未覆盖本卡核心属性需新建更精准二级；**本条是"当轮已执行项"而非待批建议**：给出结论时须同时报告执行结果（用了 `tag_rename` 还是逐卡 `memo_update`、动了哪几张、旧标签是否复查清零），确实无需改动时才直接写明「当前标签命名准确、层级合规，无需改名/归并/调整」，不得编造内容，也不得只写「无」敷衍。严禁未来预测、假设场景或"未来可能出现什么标签"；严禁提议新建卡片，严禁提议改动 SKILL.md、AGENTS.md、词表、脚本等技能文档。
3. **新建推荐**（2-3 条）：仅当"新建合理性复查"判定新建合理时输出；每条只用一句话（含标签、主题、核心论点），禁止多句段落。判定应更新原卡时写"本轮应更新原卡，跳过推荐"。

```
新建推荐：
- #顶层/二级 主题X：[一句话论点，完整表述该卡的核心内容与价值]
- #顶层/二级 主题Y：[一句话论点，完整表述该卡的核心内容与价值]
```

回复中禁止跨卡串联归纳（如"至此 X 谱系完整"），只就本卡陈述事实。

## 写成功判定与防重复

- **判定依据唯一**：脚本退出码 0 且 stderr 出现 `[成功] 已写入 memo id=`。`flomo_client.py` 写操作后强制从 `result.structuredContent.id` 取 id，取不到即打印 `[失败]` 且退出码非 0；退出码非 0 一律按失败处理，绝不重发。
- **写前幂等（硬限，重复建卡事故根因，2026-09-14 落定）**：`memo_create` 在 `flomo_client.py` 内已内置写前查重——按卡片签名（首行标签 + 第二行概念名）检索，云端已有同签名卡时直接复用其 id 不再新建（stderr 打印 `[幂等] 已存在正文相同的 memo id=`，退出码 0）。该保护不依赖调用方自觉，属脚本层硬防护。
- **返回值是包裹结构（关键坑位）**：所有工具返回均为 `{"content":[{"type":"text","text":"<内层JSON字符串>"}], "structuredContent":{...}}`，结构化数据在 `structuredContent`（如 `memos`、`id`）。脚本内读取必须走 `structuredContent` 或解析 `content[].text`，禁止直接 `result.get("memos")`（永远取不到，会造成"查重看似通过、实际没查到"而误新建）；`flomo_client.py` 已内置 `_result_memos(result)` 统一提取。**人工查重与复盘也不得靠肉眼从打印出的 text 字符串里"看到"结果来判断命中，必须以脚本代码层解析结果为准。**
- **比对用签名不用全文**：flomo 存储会转义正文特殊字符（`>`、`|` 等存成 `\u003e`、`\|`），本地与云端全文逐字比对必然不等；幂等与查重以稳定签名（首行标签行 + 第二行概念名行）为准——search 返回的 content 即使被截断（`content_truncated=true`），前两行也始终完整。禁止用全文逐字相等判断是否重复。
- **检索关键词要短**：整行概念名含全角标点时全文检索常返回 0，须用短核心词（概念名去标点的最长中文段、标签二级词、去标点全串前 8 字）逐一检索；`_dup_candidate_keywords(content)` 已内置候选集。
- **memo id 必须程序化取用**：id 是 base64 风格长串，人工转写极易差一位（差一位即指向另一张卡或返回 `memo not found`）。写入 payload 前一律用脚本从查询结果里取原始 id 字段生成请求文件，不手抄。

## 对接细节

- 端点 `https://flomoapp.com/mcp`，Bearer 鉴权（token 在 `.mcp.json`，已 gitignore）。本环境无 MCP 面板，统一走 `flomo_client.py` 直连。
- 参数：`memo_create(content；format 可选 markdown / html，省略即纯文本)`；`memo_update(id / content)`；`tag_rename(old_tag / new_tag / max_memos)`。依赖 flomo Max 会员。
- `memo_create` 与 `memo_update` 均不得传入 `linked_memos`（见执行铁律第 7 条「禁止关联卡片硬限」）；正文里的 `((memo_id))` 不会被解析为链接。
- 正文防标签误识别：flomo 扫全文把 `#xxx` 当标签，写前预判改写——`#8435` 写成"issue 8435"、`≤#150` 写成"第150位"、`C#/.NET` 用空格或"与"连接。正文斜杠不预判改写（`/xxx` 属正常书写，不构成脏标签）。

## 本地与治理

- 仓库只存技能与配置文档，不含卡片正文；`.mcp.json` 已 gitignore；`tag_tree.txt` 已 gitignore。
- **标签树本地留存（2026-09-16 落定，2026-09-18 改不入库，2026-09-20 修 limit）**：云端标签树留存本地 `tag_tree.txt`（首行 total 与采集时间，按顶层分组列二级）。每次定标签与复盘前先比数量：`tag_tree` 现采必须传 `{"limit":2000}` 拿全量（服务端默认 200 会截断；且 `limit` 须 ≥ 云端 total——2026-09-20 实测 total 升到 502 后，旧的 `limit:500` 会把 `tags` 列表截到 500 条，`len(tags)≠total` 导致无法据以重建本地文件），以 `structuredContent.total` 为云端标签总数与本地首行 total 比对——数量一致即视为云端无增删，直接以本地 txt 为标签树依据，不再重复采云端；不一致才现采云端并覆盖更新本地 txt。云端数量是权威（tag_rename 与清空都会改变数量）。本地文件属现采中间缓存，**不入库、不得 commit**。
- **推送通道（2026-09-18 复测更新）**：文档改动 commit 后自动 push 到 GitHub（远端 `shushuzn/flomo-note`，master 分支），不另等授权；称"已提交 / 已推送"必须附真实 hash 并以 `git ls-remote` 核对。推送失败多为代理或 DNS 指向坏 IP，不等于 GitHub 不可用，禁止据此下"推不上去"的结论。按序尝试：① 先清掉沙箱注入的代理直连——`env -u http_proxy -u https_proxy git -c http.proxy="" -c https.proxy="" ls-remote origin`，通了就用同样方式 push（2026-09-18 实测：注入的 `127.0.0.1:41264` 代理返 502，去代理后直连可用）；② 仍不通再拉起 `python scripts/git_tunnel.py &`（本地 CONNECT 代理，把 `github.com:443` 透传到可达 IP，SNI 与证书校验仍端到端保持 `github.com`），用 `git -c http.proxy=http://127.0.0.1:18123 -c https.proxy=http://127.0.0.1:18123 push origin HEAD`；③ 确实推不上去时提交只在本地，必须如实告知并给出 commit hash。
- 技能文档改动后跑 `scripts/audit_skill.sh`（sounding linter，目标 100/100、0 findings）自校；改动 `scripts/validate_memo.py` 后必须跑 `python scripts/test_validate_memo.py`（回归用例，退出码 0 为全过），防止表格判定与标签规则被改回误报。
- 云端状态不进 memory：标签树、卡清单、已写入规则一律现查本文件或 `tag_tree`，不靠记忆。
- 收口保持工作目录整洁：本轮产生的临时文件与请求 JSON 在收尾时清理，只留 SKILL.md、AGENTS.md 等长期文档（临时文件已由 `.gitignore` 兜底不入库）。
