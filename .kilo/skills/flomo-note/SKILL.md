# flomo 卡片笔记（云端）

本地只存本文件 + AGENTS.md + .mcp.json；卡片仅存云端 flomo。

## 能力边界（一次讲清）

flomo MCP 工具（实测）：`get_daily_review` `get_format_guide` `get_tag_guide` `memo_batch_get` `memo_create` `memo_recommended` `memo_search` `memo_update` `memory_context` `memory_user` `tag_rename` `tag_search` `tag_tree`。

写操作只有三个：
- `memo_create` 新建
- `memo_update` 覆盖某张卡（整卡替换，不保留旧文）
- `tag_rename` 全库改标签名

无 `memo_delete`（删除）：flomo 不提供「从云端移除卡片」的 API，**删除卡片只能用户在 App 手动完成**。技能侧绝不调用删除、也不主动提示用户去删。

**清空 ≠ 删除（概念区分 · 须授权）**：
- **清空** = 用 `memo_update(id, content=' ')` 把卡片正文改为空白笔记，**卡片仍留在云端、仅内容被抹除**；属区别于删除的"退役"手段，被清空的卡未来仍可用 `memo_update` 重新写入正文。
- **删除** = 从云端彻底移除卡片，技能无此能力，只能用户在 App 手动删。
- **副作用（必知）**：清空后该卡的**标签会被一并置空**——只挂在被清空那张卡上的独占标签会随之从标签树消失。**因此引用任何标签簇名前必须重新 `tag_tree` 现采，不得凭历史记录或旧日志里的簇名引用**（与"静态词表易过时"同理）。
- **执行边界**：常规 `memo_update` 写入/覆盖正文属铁律 1 的免确认写操作；但把卡片**清空为空白**属"退役"动作，**不属常规写卡，须用户明确授权**（如"清空重做""清掉这张"）后方可执行，技能不得自行发起。清空前必须先用 `memo_search`/`tag_tree`/`memo_batch_get` 确认范围（哪一张/哪几张），避免误清本就合规的卡。

无 `memo_merge`："合并卡片"做不到——`memo_update` 是覆盖不是并卡，`tag_rename` 只能并**标签名**不能并**卡片**。复盘说"合并"只指标签归并或内容聚合提议，绝不声明"已合并两张卡"。

## 执行铁律

1. 只读工具（memo_search/tag_tree/memo_batch_get/memo_recommended/get_* /memory_* /webfetch/websearch）直接做。**写操作（memo_create / memo_update / tag_rename）一律免确认**：抓取→查重→自检 EXIT=0 后直接写云，不展示等批。**禁止凭个人判断跳过写卡**：用户发链接即视为"需要写卡"，抓取成功且能提炼出任何事实/数据/观点就必须写云，不得以"内容单薄""不值得"为由跳过；仅在抓取完全失败且无替代来源时方可跳过并说明原因。
2. 带来源 URL 的卡，写入前该 URL 必须已真实抓取并基于实际内容写作；抓取失败/空 SPA 壳且无外链可追，禁止写云（不得凭域名臆测）。
3. 调 flomo 一律走 `python scripts/flomo_client.py <tool> --file <json路径>`（从文件读 JSON，避 PowerShell 引号转全角）；不写内联 JSON。
4. 写云前必查重并显式报告结论（命中什么/无重复），不敷衍。
5. 复盘改动文档须附真实 commit hash，不口头虚称"已推送"。
6. 单卡字数硬限：单卡正文（含标签段）不得超过 3 万字；超出须精简内容，禁止超 3 万字的卡写云。
7. 禁止关联卡片（硬限）：卡片正文中不得提及、引用或关联其他 flomo 卡片（包括但不限于写"与已建卡的 XXX 形成..."、"关联卡片"段落、引用其他卡片 id/标题/内容等）；禁止使用 `linked_memos` 字段设置卡片间关联。每张卡独立成文，不依赖其他卡片的上下文，不跨卡串联归纳。
8. 所有卡片均为概念卡（硬限）：每张卡围绕某一概念/主题/事件/企业进行记录和整理，后续进展用 memo_update 覆盖更新，禁止新建平行卡记录同一概念。

## 卡片格式

首行 `#标签/细分` 单独成段，第二行为概念名称（简明概括卡片主题的名词/概念，如"马尔科夫链"），空一行接正文。**所有卡片均为概念卡（硬限）**：每张卡围绕某一概念/主题/事件/企业进行记录和整理，后续进展用 memo_update 覆盖更新，禁止新建平行卡记录同一概念。**单卡单事件（硬限）**：一张卡只记录一个事件/主题/企业；多条目链接或一文多事件须按条目拆分为多张独立卡，禁止跨条目汇总、禁止多事件塞入一张卡。下方为格式示意，**尖括号 `<...>` 是说明占位，落卡时一律替换为真实内容，且禁止把"一句话核心结论"等格式提示词当作正文前缀写进卡片**：

```
#标签/细分
<概念名称>

<直接写结论句，例如：MotherDuck 于 2026-08-25 收购 Tower，补齐数据工程运行时>

要点：
- 要点一（依据）
- 要点二
```

- 结论先行：首段直接写结论句，**不要带"一句话核心结论："这类模板提示词前缀**（那是给模型看的格式说明，不是正文）。
- "要点：" 是可保留的结构标记；其它如"一句话核心结论："等纯说明性文字不得写入。
- 单卡正文（含标签段）不超过 3 万字（硬限，见执行铁律第 6 条）；超出须精简，禁止超 3 万字写云。压到够清楚即可。
- 禁止关联卡片（硬限，见执行铁律第 7 条）：正文不得提及、引用或关联其他 flomo 卡片（id/标题/内容），不得写"与已建卡的 XXX 形成..."等跨卡串联表述；每张卡独立成文。
- flomo 富文本实测：支持加粗 `**文字**`、高亮 `<mark>`、下划线 `<u>`、两级列表、空行分段；不渲染标题/引用/代码块/链接/表格/图片。
- 公式用 Unicode（∑ μ →），不写 LaTeX 美元符。

## 标签规则

- 首行标签段，多个 `#标签` 空格分隔；**每个带 `#`**，裸词不进标签系统。
- **子标签带主前缀**：`#思想/协调博弈`，不裸写 `#协调博弈`（会建出独立顶层）。
- **层级严格两级（硬限）**：标签形态仅 `#顶层/二级` 一种（例：`#科技/安全` `#思想/协调博弈`）。**禁止三级及以上**：`#科技/安全/邮件认证`、`#科技/安全/钓鱼` 这类三段路径一律非法。若主题看似需第三层，二选一：① 并入既有二级（如邮件认证/钓鱼/攻击面本就含在 `科技/安全` 定义内，直接落 `科技/安全`）；② 在合适顶层下新建二级（仍两级，免确认，仍需先查近邻确认无既有簇）。宁在二级内用正文细分，绝不下探层级。
- 顶层禁泛指词头（`#概念/` `#方法/`）；禁 emoji/特殊字符；英文词用下划线（`#Apple_seed`）。
- 新顶层/二级前先 `memo_search`+`tag_tree` 现查近邻确认无既有簇；**新建/重命名/合并标签一律免确认**。禁止为"能复用"而硬套既有标签凑数。

**标签错配防御（硬限，不可跳过）**：
1. **核实主体所属**：定标签前必须确认主体对象的真实分类（饮料/食品/美妆/日化/科技/媒体等），不得按模糊印象硬套。例：德芙是巧克力（食品），错配塞进"快消饮料"即违规。
2. **匹配事件本质而非事件载体**：概念卡按事件核心性质选标签，不按涉事品牌的行业大类硬套。例：德芙七夕暧昧文化争议，本质是青年文化/婚恋价值观事件 → `#文化/青年文化`，而非按德芙品牌行业塞进"快消"某二级。
3. **不合内容绝不硬塞（核心规则）**：既有标签确实不匹配内容时，**必须新建更精准的标签，不得硬套语义接近的既有标签凑数**。例如主题是"液冷服务器"，即使存在 `#科技/算力硬件` 也不能因为"语义接近"就硬套——只有确认主题精确属既有标签的定义范围时才复用，否则新建。先 `memo_search`+`tag_tree` 现查确认无既有簇，再免确认新建。既不允许反问用户，也不允许"宁塞勿新"。
4. **内容严格来自原文**：提炼步骤严禁编造。原文是事件报道就不写"方法论""启示"等原文没有的分析；原文是方法论文章才提炼方法论。任何原文没有的要点一律不写。

## 流程

1. **抓取**：webfetch 为主，SPA/清单站补 `curl -L -A "Mozilla/5.0"`；同名对象按域名/作者/用途消歧。
1.5. **网络搜索验证（阻塞）**：抓取后若主体为**专业术语/数学概念/科学名词/机构简称/专有名词**（如分形名称、模型代号、定理名、产品系列、组织名），**必须用 `search` 工具现查标准名称与定义**，不得凭原文简称或图片特征臆测。查证项：
   - 标准术语（英文 + 中文）
   - 命名来源/发明者/首次提出时间
   - 关键参数（维数、缩放因子、迭代规则等）
   查证结果融入卡片正文对应要点。抓取失败或内容不足以提炼事实时，**补 `search` 搜相关内容作为替代来源**；无替代则跳过写卡并说明原因。
2. **提炼**：滤营销话术，留事实/数据/因果链，不编造。
3. **定标签（含筐型判断，阻塞）**：`tag_tree` 现采完整树，命中既有簇。**选最精准标签，禁止硬塞**：既有标签不精确匹配主题时必须新建更精准标签，不得以"语义接近"为借口硬套；只有确认主题精确属既有标签定义范围时才复用。关键判断——**具体当期主题 ≠ 纯概念筐**：`/方法论` `/概念` 这类二级只收"研究怎么做"的元层面（框架、范式、通用方法），具体某政策/某事件/某产品的当期解读严禁塞入，必须落到具体主题二级（无则新建）。新建二级先现查近邻、确认无既有簇。标签深度严格两级，不得产生 `#顶层/二级/三级` 形式。
4. **查重（阻塞）**：`memo_search` 关键词扫 + `tag_tree` 列该主标签细分逐条比对（主标签维度检索常返回 0，须退回关键词+逐条比对）。两路均无命中→新建；完全重复→指原卡；部分重叠→更新原卡。**更新 vs 新建判断准则（同事件只留一张卡 · 硬限）**：**同一事件（同一次发布 / 收购 / 财报 / 政策 / 事故 / 开庭）只保留一张卡**。无论新到几篇报道、拆出几个视角（商业 / 架构 / 评测 / 生态 / 财务），全部并入同一张卡——用 `memo_update` 覆盖式合并（重组织语言、消除重复、按逻辑重排），**严禁为「不同角度 / 补评测 / 补商业 / 补生态」新建平行卡**。反模式示例：同一事件连建多卡（如 Qwen3.8 分建「架构」「商业」「评测」三张）→ 一律视为误操作，必须合并为一张。仅当新内容与原卡是**真正不同的主体或事件**（如 Qwen 架构卡 vs 浙江省数据集团、黄仁勋财报会 vs 英伟达收购 HF）→ 才新建。

**单卡单事件（汇总禁令）**：「同事件只留一张卡」不仅约束"同事件多视角不建平行卡"，也意味着**一张卡不得塞入多件独立事件/主题**，禁止跨条目汇总。
5. **写作**：按卡片格式写 1 条。
6. **写云前自检（阻塞）**：`python scripts/validate_memo.py memo_body.txt`（从文件读；也支持 `--content "..."` / `--create create.json`）须 EXIT=0（0 ERR）才许写云；任一项 ERR 先改再写，禁止把云端当草稿反复 memo_update。**自检通过即调 memo_create 写云，免确认**（判定以脚本 `[成功] 已写入 memo id=` 为准）。质检脚本强制标签严格两级（三级及以上/裸顶层直接判 ERR），与「标签规则」硬限同源。
7. **复盘（写卡后必做，须现查）**：`memo_search` 关键词扫近邻 + `tag_tree` 列同主标签细分 + `memo_recommended`（**传本卡 id**、limit 建议 20，只读近邻校验：flomo 按本卡返回关联推荐，专补关键词搜不到的语义近重复；不写 `linked_memos`）。三路逐一判断：
   - **新建合理性复查（先看）**：本卡是否其实是同一主体的新方面、本应更新既有卡？是→向用户报告"应更新原卡而非新建"并提议 `memo_update`，本轮新建视为误操作。
   - **错配核查（先看）**：本卡标签是不是具体主题误塞进 `/方法论` `/概念` 等纯概念筐？是→提议建具体二级并 `memo_update` 改标签，不得自欺写"归入既有"。
   - **硬塞核查（先看）**：本卡标签是不是与主体实际类别不符的硬塞（如巧克力→饮料、媒体事件→产业方法论）？是→提议 `memo_update` 改为正确标签，不得静默覆盖。
   - 标签归并（真可行）：两卡仅标签命名不同、本质同类 → 提议 `tag_rename`。
   - 内容聚合（只提议/可清空）：与既有卡实质重叠 → 提议"并入某卡"；若已用 `memo_update` 将原卡合并完整，冗余源卡可经 `memo_update` 清空为空白笔记（content=' ' 单空格，因空串被忽略；属上文"清空"而非"删除"，卡片仍在云端），须授权（见能力边界「清空 ≠ 删除」）。绝不声明已合并两张卡（无 memo_merge）。
   - 确无近邻：写明"已现查 tag_tree+关键词，无需调标签或聚合"。禁止只写"本轮无 memo 需更新"。
   - **复盘建议禁区（硬限）**：第 7 步收尾输出的「标签建议」一条，**落点仅限标签改名/归并/调整，严禁提议新建卡片**（新建卡片推荐由第 4 点「新建推荐」专门负责，二者功能不重复）；**严禁提议改动 SKILL.md / AGENTS.md / 顶层词表 / 脚本等技能文档**；词表补登、文档修订等不混入复盘建议，须等用户另行指令或走独立改动流程（commit+真实 hash+push）。建议中不得提及、引用或关联其他 flomo 卡片（id/标题/内容）；禁止使用 `linked_memos`。
   - **新建卡推荐（见新）**：复盘结论为"新建合理"时给出 2-3 条可新建卡片推荐（主题/标签/核心论点），格式见「写卡收尾输出格式」第 4 点；若判定"应更新原卡"则跳过。
8. **更新云端（免确认）**：`memo_update`（覆盖式）或 `tag_rename` 直接执行，**无需授权**。**更新必须重新组织语言**：新内容融入已有结构，合并同类要点、消除重复表述，按逻辑重排顺序；禁止在末尾机械追加新要点（"贴膏药"式更新）；**取最新数据、删过时旧数据（硬限）**：用最新数据替换旧数据，删除已被覆盖的过时时间节点、旧统计数字、旧状态描述（如伤亡数据只保留最新节点，不保留逐日旧值），禁止为"保留历史"堆叠旧数据造成笔记膨胀。**格式合规修正（硬限）**：更新已有卡片时，必须先回读原笔记并检查是否符合当前卡片格式要求（首行标签段、第二行概念名称为简明概括主题的名词/概念、无来源行、标签严格两级、单卡正文含标签段不超3万字等）；若原笔记不符合现有要求，必须在本次 `memo_update` 中一并修正以符合当前要求，不得保留旧格式遗留。无需求明示"本轮无 memo 需更新"。

## 写卡收尾输出格式（固定，逐项必填）

每轮写卡结束，按下述顺序回复用户；**各项都必须出现，无内容则显式写「无」，禁止静默省略**。

1. **复盘结论**：一句话写清三路现查结论（新建合理 / 应更新原卡 id=xxx / 需改标签），并显式说明已跑哪几路（memo_search 关键词 / tag_tree 同主标签 / memo_recommended）。
2. **标签建议**（一条，落点仅限标签改名/归并/调整）：**必须针对本卡当前标签的实际问题**，如发现标签命名不准确、与既有标签本质同类需归并、标签层级需调整、或当前标签未覆盖本卡核心属性需新建更精准二级标签，则给出具体改名/归并/调整建议；**若当前标签无问题，直接写明「当前标签命名准确、层级合规，无需改名/归并/调整」，不得编造内容**。**严禁讲未来预测、假设性场景或「未来可能出现什么标签」**（不实际）。**严禁提议新建卡片**（新建推荐由第 4 点专门负责），严禁提议改动 SKILL.md / AGENTS.md / 词表 / 脚本等技能文档。
4. **新建推荐**（2-3 条）：仅当复盘"新建合理性复查"判定"新建合理"时输出，沿用流程 7 格式示例：
   ```
   新建推荐：
   - #顶层/二级 主题X：[一句话论点]
   - #顶层/二级 主题Y：[一句话论点]
   ```
   若判定"应更新原卡"则写"本轮应更新原卡，跳过推荐"。

硬限：第 2 项内容必须真实给出（禁止写"无"来敷衍）；回复中禁止跨卡串联归纳（如"至此 X 谱系完整"），只就本卡陈述事实。

## 写成功判定（防重复写）

`flomo_client.py` 写操作后强制从 `result.structuredContent.id` 取 id，stderr 打印 `[成功] 已写入 memo id=...`；取不到则 `[失败]` 且退出码非 0。**判定依据唯一**：脚本退出码 0 + stderr 出现 `[成功] 已写入 memo id=`。退出码非 0 一律按失败，绝不重发。

## 对接细节

- 端点 `https://flomoapp.com/mcp`，Bearer 鉴权（token 在 .mcp.json）。本环境无 MCP 面板，统一走 flomo_client.py 直连。
- `memo_create(content；format 可选 markdown/html，省略即纯文本)`；`memo_update(id/content)`；`tag_rename(old_tag/new_tag/max_memos)`。依赖 flomo Max 会员。
- 禁止使用 `linked_memos` 关联卡片（见执行铁律第 7 条）；`memo_create` 和 `memo_update` 均不得传入该字段；正文 `((memo_id))` 不被解析为链接。
- 正文防标签误识别：flomo 扫全文 `#xxx`/`/xxx` 当标签。写前预判改写——`#8435`→"issue 8435"、`≤#150`→"第150位"、`C#/.NET`→空格或"与"连接。
